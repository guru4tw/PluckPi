## 〇、這份設計怎麼做出來的(套用影片方法)

影片的重點是：不要直接說「把網站設計好」，要先問**這領域最好的人用什麼流程、什麼工具、什麼驗收標準**(#5、#6、#19)，再照著做；而且要評**過程**，不只評結果(#4)；驗收要靠**外部硬證據**，不靠同一個 session 自評(#20)。

| 頂尖網站架構師的做法 | 在本設計的落點 |
|---|---|
| 先讀**現況與原始資料**，不從空白頁開始 | 讀過 `index.html`、`build_site.py`、`style.css`、`topics.md`、`knowledge.json`(19 條，全已整理)，第一節列出現況問題 |
| 決策都要能**追溯到原則**，不靠品味 | 每個決策附「為什麼」；用 GOV.UK 設計原則(少即是多、先做需要的)、WCAG 2.2、Google 多語網站指引(hreflang、不強制依語言轉址)、W3C 語言標記(BCP 47)當準則 |
| **漸進增強**：先有能用的 HTML，再疊 JS | 所有內容由 SSG 輸出成完整 HTML；JS 只負責搜尋、篩選、記住進度。關掉 JS 網站照樣能讀 |
| **預算先定**，再設計 | 第六節定效能、無障礙、大小預算，CI 量測，超標就紅燈 |
| **驗收用硬證據**：工具量測 > 人眼 > 模型自評 | Lighthouse CI、axe、HTML 驗證、連結檢查；中文整理內容另跑「對原文查核」 |
| **少即是多**(影片 #2：好產品是按鈕更少) | 第二節逐項刪掉現有 UI 元素，每頁只留一個主要動作 |
| **對抗式審查**(影片 #7–#9) | 本文件完稿後由獨立子代理逐條找錯，裁判後修正，結果記在第九節 |

## 二、極簡 UI

### 原則

1. **一頁一件事**：首頁 = 選起點；主題頁 = 順著讀；條目頁 = 讀懂一件事。
2. **內容就是介面**：不放輪播、彈窗、漢堡選單、側欄、浮動按鈕。
3. **顏色只當輔助訊號**：紅／黃／藍只用在皮克敏種類標記；難度改用**形狀 + 文字**(葉／芽／花圖示)，取代現有 `--lv1/2/3` 顏色。版面本身是黑白灰。
4. **兩種字級 + 一種小字**：標題、內文、註記。間距用 8px 格線。
5. **每個元素都要通過「拿掉會怎樣」測試**：拿掉沒人會想念的，就拿掉。

### 頁面骨架(全站共用)

```
┌────────────────────────────────────────────┐
│ 拔拔道場 ●●●                    [搜尋]  中│EN │  ← 頁首只有 3 樣
├────────────────────────────────────────────┤
│                                            │
│   (單欄內容，最寬 68 字寬，置中)              │
│                                            │
├────────────────────────────────────────────┤
│ 出處與授權 · 非官方粉絲站 · GitHub            │  ← 頁尾一行
└────────────────────────────────────────────┘
```

### 首頁(從 9+ 個操作 → 2 個)

```
拔拔道場
皮克敏知識，一層一層剝開。每一條都有出處。

  你在玩哪一代？  [ 1 ] [ 2 ] [ 3 ] [ 4 ] [ 其他 ]      ← P3 才加(見下)，記在瀏覽器

  ◎ 道場地圖(7 個主題，洋蔥同心圓或直列，依學習順序)
    1 入門基礎   6 條   ●●●○○ 已讀 3
    2 皮克敏圖鑑 10 條
    …

  [ 繼續上次:藍色皮克敏 → ]                            ← 有閱讀紀錄才出現
```

| 現有元素 | 處置 | 理由 |
|---|---|---|
| 三步驟說明條(主題→條目→出處) | 改成標語一句話 | 介面本身就體現三層，不需要說明書 |
| 4 個難度鈕 | 移到主題頁 | 難度是「讀到哪」的概念，屬於主題內 |
| 只看本週新增 | 改為 RSS／「本週新知」一個連結 | 回訪者用，不該佔新手的首屏 |
| 統計列 | 移到頁尾小字 | 對讀者沒有行動意義 |
| 搜尋框 | 留在頁首 | 熟手的主要入口 |
| **新增(延後到 P3)**：遊戲代數選擇 | 唯一的設定 | 要等 `detail.by_game` 有內容才有用。現有 `games` 只是「出現在哪幾代」，19 條裡 12 條四代全有，現在做會是一個沒作用的按鈕。選了某代時，不含該代的條目**淡化不隱藏**；選項依資料產生(含 Hey! Pikmin、Pikmin Bloom 歸「其他」) |

### 技術選擇(UI 層)

| 項目 | 採用 | 不採用與理由 |
|---|---|---|
| 版面 | 手寫 CSS(一個檔)，CSS 變數、`clamp()` 流體字級、邏輯屬性(`margin-inline`)、`:has()` | Tailwind／Bootstrap：一個 5KB 的站不需要框架，還要多一個建置步驟 |
| 字型 | 系統字型堆疊(PingFang TC、Noto Sans TC、Microsoft JhengHei) | 中文網路字型動輒數 MB，首屏會卡 |
| 圖示 | 自繪 inline SVG(葉、芽、花代表三種難度，呼應皮克敏頭上的葉→芽→花) | 任天堂官方圖：版權問題 |
| 展開收合 | 原生 `<details>/<summary>` | 自寫 accordion：鍵盤、螢幕報讀、無 JS 全都要自己補 |
| 暗色模式 | `prefers-color-scheme`(已有) | 手動切換鈕：多一個按鈕，極簡原則下先不加 |
| 動畫 | 只有展開時 150ms 淡入；`prefers-reduced-motion` 時關閉 | 裝飾性動畫 |

## 三、中英文語系自動切換

### 核心決策：**每個語言一組獨立網址**，自動判斷只發生在根網址

```
/                 ← x-default:只做語言判斷與轉址(含兩個語言的手動連結當後備)
/zh-hant/         ← 中文首頁
/zh-hant/topics/pikmin/
/zh-hant/k/red-pikmin/      ← 單條知識
/en/              ← 英文首頁
/en/topics/pikmin/
/en/k/red-pikmin/
```

**為什麼不在同一頁用 JS 換字？** 搜尋引擎只看得到一種語言、分享出去的網址無法指定語言、關掉 JS 就壞。業界做法(MDN、Apple、GOV.UK 多語版)都是一語言一網址。

**為什麼只在根網址自動轉？** Google 的多語網站指引建議不要依讀者語言自動轉址，並建議用 `x-default` 當沒有對應語言時的後備頁。自動轉址會讓讀者和爬蟲都看不到另一個語言的版本。所以內容頁永遠不轉址，只有 `/` 這個「入口頁」(hreflang 標成 `x-default`)做判斷。入口頁本身也要有**可被索引的真實文字**(站名、一句介紹、兩個語言的大連結與說明)和三條 hreflang，不能只有一段 script。

**為什麼用 `zh-hant` 而不是 `zh`？** 未來要加簡體(`zh-hans`)時不用改既有網址。網址一旦公開就不改。在那之前，簡體讀者(`zh-CN`、`zh-Hans`)也導到繁中。

**SEO 搬家**：現在被收錄的是 `/` 這一頁。改版時 `/zh-hant/` 的 canonical 指向自己，`/` 改為 x-default 入口；預期中文首頁的排名會有一段過渡期，所以 P1 上線後要在 Search Console 觀察兩週。

### 判斷順序(根網址 `/`)

```
1. 讀者曾手動選過語言(localStorage `pp-lang`)  → 用它
2. navigator.languages 依偏好順序逐一比對：
     zh-*(含 zh-TW、zh-HK、zh-CN)→ zh-hant
     en-*                          → en
     第一個比對到的就用
3. 都沒比對到(例如日文、韓文)    → 不轉址，留在入口頁讓讀者選
4. 沒有 JS                        → 同上，頁面本身就是「中文 / English」選擇頁
```

```html
<!-- / (x-default) 的 <head> 內，放在任何 CSS 之前，避免閃一下 -->
<script>
(function(){
  var OK={'zh-hant':1,'en':1}, saved=null;
  try{saved=localStorage.getItem('pp-lang')}catch(e){}
  var pick=OK[saved]?saved:null, ls=navigator.languages||[navigator.language||''];
  for(var i=0;!pick&&i<ls.length;i++){
    if(/^zh\b/i.test(ls[i]))pick='zh-hant'; else if(/^en\b/i.test(ls[i]))pick='en';
  }
  if(!pick)return;                                   // 比對不到：留在入口頁讓讀者選
  var base=location.pathname.replace(/[^/]*$/,'');   // /PluckPi/ (project site 子路徑)
  location.replace(base+pick+'/'+location.search+location.hash);
})();
</script>
<!-- <body> 內：真實文字 + 兩個大連結，無 JS 或比對不到時就是這頁 -->
```

### 切換鈕

- 頁首右上 `中 │ EN`，連到**另一語言的同一頁**(不是回首頁)。
- 點擊時寫入 `pp-lang`，之後從根網址進來就記得。
- 每頁 `<head>` 都有三條 `<link rel="alternate" hreflang>`：`zh-Hant`、`en`、`x-default`；`sitemap.xml` 也列出 alternates。
- `<html lang>` 依語言設 `zh-Hant` / `en`。這不只是 SEO：瀏覽器靠它挑中文字形與斷行規則，螢幕報讀靠它選發音。

### 翻譯的三種文字，各有來源

| 文字類型 | 例子 | 存在哪 | 誰產生 |
|---|---|---|---|
| 介面字串 | 「搜尋」「出處」「繼續上次」 | `Docs/i18n.json`(一個檔，`{key:{zh-hant, en}}`) | 人工；build 時注入 HTML，JS 需要的部分嵌成 `<script type="application/json">` |
| 主題脈絡 | 主題名、主題說明 | `Docs/topics.md` 擴充標題格式 | 人工 |
| 知識內容 | 摘要、重點、詳解 | `Docs/knowledge.json` 加 `_en` 欄位 | curate.py 一次產兩種語言；沒有就用後備 |

`topics.md` 擴充用**具名欄位**而不是多加位置欄(位置欄在難度可省略時會有歧義)：

```markdown
## 2. 皮克敏圖鑑 (pikmin) · 入門
> 各色皮克敏的特性、免疫與用途。選對顏色就是成功的一半。
>> en: Pikmin Types — Each Pikmin type's traits, immunities and uses.
- Purple Pikmin | 紫色皮克敏 | 進階 | 先讀=Red Pikmin
```

**這需要改 parser，不是自動相容。** 現在 `common.py` 的 `HEADING_RE` 用 `(.+?)` 抓主題名，若把英文寫在標題裡會被默默吞進中文名；`ITEM_RE` 遇到第 4 欄會讓 `title_zh` 變成「紫色皮克敏 | 進階 | 先讀=…」，而且不報錯。所以 P1 要：改寫兩個 regex(`>>` 開頭的英文行、`key=value` 欄)，並先寫 `unittest` 涵蓋舊格式、新格式、省略難度三種情況；無法解析的行要**報錯**，不准默默吞掉。

### 英文版的後備規則(零成本也能上線)

英文內容的原料就是 Pikipedia 英文原文，所以英文版天生比中文版好補：

- `summary_en` 沒有 → 用 `excerpt_en` 的第一句。
- `key_points_en` 沒有 → 該層不顯示。
- 中文版的 `summary_zh` 沒有 → 照現在的做法顯示英文原文並標「待整理」。
- 現有 19 條都沒有 `summary_en`，只靠後備的話英文版會很單薄。**`/en/` 的上線門檻**：至少 3 個主題、各主題半數以上條目有 `summary_en` + `key_points_en`；之前英文頁先加 `noindex`。

### 專有名詞一致性：`Docs/glossary.md`

皮克敏的中文譯名有官方繁中名、日文音譯、玩家俗稱三套(例如現在 `topics.md` 的「查比」來自日文チャッピー)。新增一份人工維護的術語表，curate.py 翻譯時必須讀它，build 時也拿它做「同一英文名對到多個中文名」的檢查：

```markdown
| English | 繁中(本站用) | 依據 | 其他叫法 |
|---|---|---|---|
| Bulborb | (待查官方繁中名) | 官方繁中版遊戲內名稱 | 查比、大嘴怪 |
```

依據欄要填官方遊戲內文字或任天堂繁中官網，查不到就標「玩家通稱」。這是**事實查核類任務**(影片 #11)，適合單獨一個 thread 要求逐條找一手來源。

## 四、撥洋蔥式教學體驗

皮克敏的母艦就叫洋蔥(Onion)，所以「撥洋蔥」同時是網站的教學方法和品牌意象。

### 兩個尺度的洋蔥

**尺度一：一張卡片內(讀懂一件事)** — 由外到內，每撥一層要多花一點時間，也多得到一點東西。讀者在任何一層停下都已經有收穫。

| 層 | 名稱 | 內容 | 閱讀時間 | 預設 | 資料欄位 |
|---|---|---|---|---|---|
| 1 外皮 | 一句話 | 這是什麼、為什麼重要 | 5 秒 | 展開 | `summary_{lang}` |
| 2 第二層 | 重點 | 2–4 條可行動的事實(免疫什麼、怎麼培育) | 30 秒 | 收合 | `key_points_{lang}` |
| 3 第三層 | 怎麼用 | 實戰用法、**各代差異**、常見誤解 | 2 分鐘 | 收合 | `detail_{lang}`:`{use, by_game, myths}` |
| 4 芯 | 原文與出處 | 英文原文摘錄 + 來源・版本・授權・查閱日 | 隨意 | 收合 | `excerpt_en`、`source` |

- 用原生 `<details>` 實作，每層 summary 寫「剝開：重點(3)」這樣**預告裡面有什麼**，讀者才知道值不值得點。
- 第 3 層的「各代差異」會依首頁選的遊戲代數**優先顯示該代**，其他代收在後面。
- 出處永遠在最內層但**永遠存在**：卡片外層也有一行小字「出處：Pikipedia」，直接連原頁。引用規範不因教學設計而縮水。

**尺度二：整個道場(學會一個領域)** — 三個難度就是三層洋蔥圈。

```
        ┌───────── 達人(花)─────────┐
        │   ┌───── 進階(芽)─────┐   │
        │   │   ┌─ 入門(葉)─┐   │   │
        │   │   │  7 主題   │   │   │
        │   │   └───────────┘   │   │
        │   └───────────────────┘   │
        └───────────────────────────┘
```

- **主題頁預設展開「該主題最低一層有條目的難度」**(原生生物目前全是進階，就從進階開始)，更深的層用 `<details>` 收在「剝下一層：達人 1 條 →」裡。不靠 JS；收合內容仍在 HTML 中，搜尋引擎讀得到，但瀏覽器的頁內搜尋(Ctrl-F)在部分瀏覽器找不到收合內容，所以主題頁頂端另列全部條目標題的目錄。
- 皮克敏的成長本來就是 葉 → 芽 → 花，直接拿來當三種難度的圖示，皮克敏玩家不用解釋就懂。

### 條目之間的路徑(「下一步讀什麼」)

- **主題內順序 = `topics.md` 裡的行序**。作者排順序就是在排教學順序，不另開欄位。卡片底部顯示「下一條：黃色皮克敏 →」。
- **跨主題前置**(選配)：`topics.md` 一行可加 `先讀=Onion` 欄，build 時檢查被引用的頁名存在，並在卡片顯示「先讀：洋蔥」。
- 避免做成強制關卡：任何條目都能直接進入，前置只是建議。

### 進度(只存在讀者自己的瀏覽器)

- `localStorage` 記「讀到第 3 層以上的條目」與「上次讀的條目」，首頁顯示「繼續上次」與每個主題的已讀數。
- 讀不到 localStorage(無痕視窗等)時就當作沒進度，介面不出錯。
- 不做帳號、不上傳、不追蹤。

### 自我檢查(第二階段)

第 3 層末端可放一題「考考你」(例：「火焰陷阱前要派哪一色？」)，點一下才顯示答案。題目由 curate.py 從原文產生、人工抽查。先不做計分，避免把道場變成考試。

## 五、架構與技術選擇

### 維持的部分(已經是對的選擇)

- **三層全靜態**：GitHub Actions(排程)+ Python(收集與建站)+ GitHub Pages(前端)。全免費、無伺服器可壞。
- **Python 標準庫零依賴**：collect／verify／build 不裝套件，本機 Python 3.9 可跑。
- **收集與整理分層**：沒有 API 金鑰也能上線。

### 要改的部分

| 改動 | 做法 | 為什麼 |
|---|---|---|
| **單一卡片渲染器** | 所有卡片(含首頁)由 `build_site.py` 輸出成 HTML；JS 只對既有 DOM 做顯示／隱藏 | 消除 `card()` / `card_html()` 雙份同步；無 JS 可讀；搜尋引擎看得到首頁內容 |
| **每條知識獨立網址** | `/{lang}/k/{slug}/`。slug 由 **`collect_pikipedia.py` 建立條目時**從 `title_en` 產生(小寫、非英數轉 `-`、撞名加 `-2`)，之後永不改。build 只讀資料、不寫回 `Docs/`，維持「建站 = 資料的純函數」 | 可分享、可被索引、可被其他條目連結。19 條 × 2 語言 = 38 頁，規模沒問題 |
| **模板** | 繼續用 Python f-string，但把頁面骨架、卡片、各層拆成小函式並以 `lang` 參數化 | 加 Jinja2 會打破零依賴；目前頁面種類少(首頁、主題、條目、來源)，函式就夠 |
| **前端 JS** | 一個 vanilla ES module，目標 < 6KB 壓縮後；功能只有搜尋、遊戲代數篩選、進度 | 沒有需要框架的互動 |
| **搜尋** | build 時每個語言產一份精簡索引 `search-{lang}.json`(標題、別名、摘要、重點，含另一語言標題)；瀏覽器端子字串比對 | 中文不需要斷詞就能子字串搜尋；英文名在中文站也搜得到(玩家常打英文名) |
| **舊網址相容** | 舊網址轉址頁由 **build 產生**(build 每次 `rmtree` 重建，手寫的轉址頁會被刪)。轉址頁含 `canonical`、`<meta refresh>`，加一小段 JS 把 `#pikipedia-1188` 這類錨點對應到 `/zh-hant/k/<slug>/`(meta refresh 會丟掉 `#`)。刪除的條目記在 `Docs/retired.json`(slug → 去向)，build 依它產轉址頁 | GitHub Pages 不能發 301；已被收錄、已被分享的連結不能斷 |
| **workflow 跟著改** | `weekly.yml` 的 `git add` 加上 `zh-hant/ en/` 與 feed；Lighthouse 等檢查只擋 PR，**不擋**每週自動更新(失敗就開 Issue) | 不然新產物永遠不會被 commit；檢查紅燈也不該讓內容停更 |

### 資料模型擴充(`Docs/knowledge.json`，只加欄位，不改舊欄位)

```jsonc
{
  "id": "pikipedia-1188",
  "slug": "red-pikmin",                       // 新：網址用，首次產生後固定
  "topic": "pikmin", "level": "入門",
  "title_zh": "紅色皮克敏", "title_en": "Red Pikmin",
  "summary_zh": "…", "summary_en": "…",       // 第 1 層
  "key_points_zh": ["…"], "key_points_en": ["…"],   // 第 2 層
  "detail_zh": { "use": "…", "by_game": {"Pikmin 4": "…"}, "myths": ["…"] },  // 新：第 3 層
  "detail_en": { "...": "..." },
  "grounding": [ {"claim": "免疫火焰", "excerpt_span": "immune to fire"} ],   // 新：每條重點對應原文哪句
  "spoiler": false,                            // 新：劇透條目
  "excerpt_en": "…", "games": ["…"], "source": { "...": "..." },
  "status": "curated", "curated_by": "claude-opus-5-5", "curated_at": "…"
}
```

- 難度值仍存中文(`入門/進階/達人`)以相容既有資料；英文顯示由 `i18n.json` 對應成 `Beginner / Intermediate / Master`。
- `grounding` 是把影片「評過程」(#4)落到資料：每條重點都要指出它來自原文哪一句。`excerpt_span` 必須是 `excerpt_en` 的**逐字子字串**(build 可機械檢查)；「中文重點是否忠於那句英文」則由審查模型判斷、人工抽查。對不上的重點標警告並計入未查核率，**先不擋上線**(curate.py 尚未實測，不宜當硬門檻)。
- 範例中的 `curated_by` 是 curate.py 產生時的樣子；現有 19 條都是 `manual`。

## 七、高手會多想到的事

### 內容與教學

1. **劇透分級**：四代的遇難者、隱藏頭目、結局相關條目設 `spoiler: true`，卡片外皮模糊並顯示「劇透：四代後期」，點了才看。考據類主題(lore)最需要。
2. **各代規則不同是最大的坑**：同一隻生物在不同代弱點不一樣。所以第 3 層的 `by_game` 和首頁的代數選擇是核心設計，不是附加功能。
3. **內容會過期**：原文 `revid` 變了就標 `source_changed_at`(已有)，卡片顯示「原文已更新，整理內容待複核」，而不是默默顯示舊整理。
4. **「下一條」比「相關條目」好**：相關推薦很容易變成一堆連結；教學需要的是一條明確的路。先做「下一條」，相關推薦等條目超過 100 條再說。

### 讀者

5. **色盲**：紅／藍／黃皮克敏每個色點旁都有文字或形狀標記，不只靠顏色(WCAG 1.4.1)。
6. **觸控目標 ≥ 44px**：讀者多半是邊玩 Switch 邊用手機查。
7. **單手、橫向、離線**：手機直向單欄為主；第二階段可加 Service Worker 讓讀過的頁面離線可看(只快取靜態檔，不做推播)。
8. **簡體讀者**：`zh-CN` 先導到繁中；確認有流量後再用 OpenCC + 術語表產 `/zh-hans/`。

### 法律與信任

9. **CC BY-SA 的「相同方式分享」**：中文整理是 Pikipedia 的衍生作品，必須同樣以 CC BY-SA 釋出(已在頁尾聲明)；英文的 `summary_en`、`key_points_en` 也是衍生作品，`/en/` 每頁要有同樣的英文出處與授權行。
10. **商標與圖片**：不用任天堂官方圖片、Logo、遊戲截圖；所有視覺元素自繪。頁尾維持「非官方、無關聯」聲明。
11. **隱私**：不放追蹤 Cookie，也就不需要 Cookie 同意彈窗(也符合極簡)。若要流量統計，用不設 Cookie 的方案(如 GoatCounter)，但它是第三方腳本加帳號，**先不做**；需要時再評估，並在頁尾說明。

### 工程

12. **網址是承諾**：slug 首次產生就寫回資料，之後標題改了也不變；刪除的條目留轉址頁。
13. **建置可重現**：同一份 `knowledge.json` 在不同天建兩次，輸出要完全一樣，Actions「有變動才 commit」才準確。**現在的 `build_site.py` 做不到**：它把 `TODAY` 寫進首頁「最近更新」、根 `knowledge.json` 的 `updated_at`、每個 sitemap `<lastmod>`。改成：「最近更新」與 `updated_at` 取資料裡最大的 `fetched_at`/`curated_at`，sitemap 用各條目自己的日期。
14. **結構化資料**：條目頁輸出 JSON-LD `LearningResource`(含 `educationalLevel`(依語言對應成文字)、`inLanguage`、`isBasedOn` 指向原頁、`license`)，讓出處與授權機器可讀。這是標註，不會帶來 Google 複合式搜尋結果，不要期待 SEO 加分。
15. **本週新知 Atom feed**：`/{lang}/feed.xml`，build 時產生，零成本，回訪者可訂閱；取代首頁的「只看本週新增」按鈕。
16. **社群預覽圖**：每個主題一張自繪 SVG 轉 PNG 的 OG 圖，分享到 LINE／Discord 時才不會是空白卡。

### 流程(影片方法的長期落地)

17. **整理內容三關**：curate(Opus 產生)→ grounding 審查(Sonnet 找出原文沒說的)→ 人工只看被標出的那幾條。人只做判斷，不做搬運(影片 #16「不當傳送帶」)。
18. **蒸餾審稿原則**(影片 #21)：人工改過的整理內容，每季彙整一次「改了什麼、為什麼」，濃縮成 `Docs/curation_rules.md`，之後餵給 curate 與審查。
19. **模型更新就重跑 A/B**(影片 #15、#27)：新模型出來時，拿 10 條已人工確認的條目重整理一次，並排比較，再決定要不要換 prompt 或模型。
