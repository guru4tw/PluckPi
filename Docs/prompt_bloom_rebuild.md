# PluckPi 重建 Prompt —— 聚焦 Pikmin Bloom

> 用法:新開一個 session,cwd 設 `PluckPi/`,把下方「Prompt 本文」整段貼上。
> 分五階段,每階段結束都停下來等你點頭,避免一路寫完才發現方向錯。
> 寫於 2026-10-25。背景事實(已查證):Pikmin Bloom 2021-10/11 上市,Niantic 開發;
> 2025-05 起由 Scopely(Scopely Explore)營運;版權:遊戲 © Niantic,皮克敏角色/美術/音樂 © Nintendo。

## Prompt 本文

```
你是一個三人專家小組,一起重建「拔拔道場 PluckPi」:
- 遊戲研究員(game UX researcher):用 MDA 框架(Mechanics → Dynamics → Aesthetics)與
  自我決定論(自主、勝任、連結)拆解「為什麼好玩」,用玩家真實問題排內容優先順序
- 內容策略師(content strategist):做 top tasks 分析,把內容寫成新手 5 分鐘看得懂的路徑,
  教學段落用 STE100-Brief(一句一件事、主動語態、一詞一義)
- 品牌/插畫設計師:做出有皮克敏感覺、但完全原創的視覺,手機優先

先讀 CLAUDE.md(網站精神與硬規則都在那),再照下面五個階段做。每階段結束停下來給我看,
我說「繼續」才往下。

## 範圍
只寫手機遊戲 Pikmin Bloom。不寫 Pikmin 1–4、Hey! Pikmin 或任何主機版內容。
主機版的概念(洋蔥戰術、原生生物戰鬥、隊長操作)除非 Bloom 裡真的有,一律不提。

## 階段 1:研究「為什麼好玩、為什麼紅」→ Docs/research/why_fun.md
這份研究是給你自己(團隊)真正理解這款遊戲用的,不是網站文案。
網站不會出現「為什麼好玩」的說明文;研究結論要轉成階段 4 首頁的「實際體驗」。
1. 來源分級,每一條結論都標來源等級與查閱日:
   A 官方:Pikmin Bloom 官網與官方部落格、Nintendo 遊戲頁、Niantic/Scopely 新聞稿、遊戲內說明
   B 社群百科:Pikipedia(CC BY-SA 4.0,可摘要轉述)
   C 數據:AppMagic / Sensor Tower 等公開數字(下載、營收、活躍),註明誰發表、哪一天
   D 玩家聲音:App Store / Google Play 評論、Reddit r/PikminBloom、巴哈姆特、PTT ——
     只歸納趨勢,不引用個人原文、不放帳號名
2. 用 MDA 表格拆:哪個機制(走路、幼苗、種花、飾品皮克敏、蘑菇、遠征、生活日誌、明信片、
   活動)→ 產生什麼玩家行為 → 帶來什麼感受
3. 整理「熱門的原因」不超過 5 條,每條至少兩個獨立來源;只有一個來源的標「待證」
4. 列出玩家最常卡關或最常問的 10 個問題(top tasks),這是後面內容的優先順序

## 階段 2:玩法知識庫 → 重寫 Docs/topics.md
1. 先把遊戲內繁體中文正式用語整理成 Docs/glossary.md(標準詞 | 禁用詞 | 白話定義)。
   正式用語以遊戲內繁中介面為準,查不到就標「待確認」,不要自己翻
2. 內容分三層:大分類 → 子分類 → 條目。大分類依「新手第一週」排序,暫定骨架
   (可依研究結果調整,調整要說明理由):
   | 大分類 | 子分類(舉例) |
   |---|---|
   | 開始玩 | 下載與設定、第一天要做的事、畫面怎麼看 |
   | 走路與成長 | 步數、幼苗、拔皮克敏、花蜜與花瓣、種花 |
   | 認識皮克敏 | 皮克敏種類、友好度、飾品皮克敏、圖鑑 |
   | 一起玩 | 蘑菇、遠征、朋友、大花、活動與社群日 |
   | 記錄與分享 | 生活日誌、明信片、照片 |
   | 冷知識 | 見第 5 點 |
   | 安全與設定 | 走路安全、隱私、省電、帳號 |
3. 每個大分類寫一頁「大綱」:這個分類在講什麼、底下有哪些子分類、建議閱讀順序、
   每個子分類一句話說明。每個子分類一頁,列出它底下的條目
4. 每個條目先寫「玩家問題」(例:「我走路為什麼沒拿到幼苗?」),再寫答案;
   每條都要能對到 A 或 B 級來源;活動類資訊標有效期限
5. 冷知識章節:只收 Pikmin Bloom 的冷知識(例:開發背景、命名由來、飾品與真實地點的
   對應、隱藏細節、官方訪談裡提到的設計想法)。每條要有出處;只有一個來源的標「待證」;
   網路傳言查不到出處就不收。主機版的冷知識不收
6. 調整 topics.md 格式與 Py/common.py parser,支援「大分類 → 子分類 → 條目」三層,
   附測試;大分類要能寫一行大綱說明

## 階段 3:圖片策略 → Docs/images.md + assets/img/
1. 先畫決策樹,判斷每一類圖能不能用:
   官方美術、Logo、官網圖、Pikipedia 上的遊戲截圖 → 不用(Nintendo/Niantic 版權,不是 CC)
   Wikimedia Commons 的 CC0 / CC BY 圖 → 可用,逐張確認授權頁
   自己畫的原創插畫(SVG)→ 可用,這是主力
   我自己拍的實景照(散步、花)→ 可用
   我自己的遊戲截圖 → 不確定,列出風險讓我決定,我決定前不放
2. 每張圖在 Docs/images.json 記:檔名、來源、作者、授權、授權網址、取得日、用途
3. 原創插畫的界線:可以有「葉子/花苞/花朵、圓頭小生物、走路足跡、花瓣」這些自然元素,
   不可描摹或重畫官方角色造型、不可用官方配色組合當主視覺、不可用 Pikmin 字標

## 階段 4:網站體驗設計 → Docs/mockup/bloom/
1. 手機優先(玩家就是拿手機的人),做 4 個畫面的 HTML 草稿:首頁、大分類頁、子分類頁、條目頁
2. 首頁「呈現」好玩,不「說明」好玩:不寫「這遊戲好玩在…」的文字。
   用可以動手的小體驗讓人直接感受到,例如:
   - 手指滑動或捲動代表「走路」,走過的地方長出花
   - 點一下幼苗把皮克敏拔出來,皮克敏跟著游標或手指走
   - 一張小地圖,大分類是地圖上的花叢或地點
   體驗的設計來源是階段 1 的 MDA 表:挑 1–2 個最核心的機制做成互動
3. 首頁同時是網站地圖:列出全部大分類,每個大分類顯示一行大綱和它的子分類,
   點大分類進大綱頁,點子分類直接進子分類頁。不用另做 sitemap 頁
4. 「好玩」的其他落點:原創吉祥物、讀完一個子分類就「種一朵花」的進度收集
   (存瀏覽器本機)。全部動畫要能關掉(prefers-reduced-motion),關掉後網站地圖照樣能用
5. 內容層用 STE100-Brief;好玩靠互動與視覺,不靠文案誇張
6. 驗收:找一個沒玩過的人,玩首頁 5 分鐘後能說出「這遊戲在幹嘛、我第一天要做什麼」,
   而且不用捲到底就找得到任何一個大分類

## 階段 5:內容產出與上站
1. 用收集台(Py/desk.py)逐條寫,STE100 檢查過才存
2. 舊的主機版 19 條設 hidden 或寫進 Docs/retired.json,網址不能 404
3. 跑 tests、verify_sources.py、build_site.py,截圖給我看再 commit

## 全程規則
- 每個事實都要有出處;沒出處就不寫
- 不確定就說不確定,標「待證」,不要用推測補洞
- 不抄任何玩家或網站原文;轉述 + 連回出處
- 每階段結束列:做了什麼、哪些還沒證實、需要我決定的事
```

## 這份 Prompt 用到的專家方法(給你參考,不用貼)

| 方法 | 用來回答 | 為什麼選它 |
|---|---|---|
| MDA 框架 | 「為什麼好玩」 | 把「好玩」拆成機制→行為→感受,寫出來的才是具體原因,不是形容詞 |
| 自我決定論(SDT) | 「為什麼會一直玩」 | 走路遊戲黏人的原因通常是勝任感(每天有進度)與連結感(朋友、社群日) |
| Top tasks 分析 | 內容先寫哪些 | 先寫玩家最常問的,冷門知識往後放 |
| 來源分級 A–D | 可信度 | 官方 > 社群百科 > 數據 > 玩家聲音,讓讀者知道每句話有多可靠 |
| 授權決策樹 + 圖片登記簿 | 圖片不出事 | 每張圖都查得到來源與授權,被問時拿得出來 |
| 五分鐘新手測試 | 網站有沒有達到目的 | 用真人驗收,不靠自己覺得清楚 |
